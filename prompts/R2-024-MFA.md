# R2-024 — Multi-factor authentication (TOTP + recovery codes)

**Context.** v2.0 (R2) backend, Part D (account security). Depends on the identity model built by **R2-001**
(the `user` table, the Admin/Operator built-in roles) and auth/sessions built by **R2-003** (`/v1/auth/*`, the
hashed `user_session`, `TokenFilter`/`AccessPolicy`), with the `self.*` gating from **R2-004**. Self-service
scope `read` for the enrolling user; enforcement applies to roles. Crypto stays standard and unexotic — a
published, audited TOTP implementation, no hand-rolled primitives.

**Goal.** TOTP enrollment with single-use recovery codes. Optional for everyone, **required for Admin and
Operator**. The owner's recommendation (confirmed): required for Admin/Operator, optional otherwise.

## Build

1. **TOTP secret + enrollment** (`ai.foresignal.security` or a new `ai.foresignal.mfa`). `enrollMfa` generates a
   Base32 TOTP secret (RFC 6238), stores it **encrypted** and **pending** on the user, and returns
   `MfaEnrollment` (`secret`, `otpauthUri` `otpauth://totp/ForeSignal:<email>?secret=…&issuer=ForeSignal`, and
   an inline `qrSvg` of that URI). Use a published, permissively-licensed TOTP library verified on Maven Central
   (e.g. `dev.samstevens.totp`) or RFC 6238 over the JDK's `javax.crypto` HMAC — do not hand-roll the HOTP
   truncation. For `qrSvg`, use a small permissively-licensed QR encoder verified on Maven Central, or leave
   `qrSvg` null (the schema allows it) and rely on `otpauthUri`.

2. **Verify / activate.** `verifyMfa` (`MfaVerifyRequest.code`) checks the current 6-digit code against the
   pending secret (with a ±1 step window and replay protection — reject a code already used). On success, MFA
   becomes active (`mfa_enabled`, `mfa_enrolled_at`) and a set of single-use **recovery codes** is generated,
   stored **hashed** via `TokenHasher`, and returned once in the response body as `MfaRecoveryCodes`. The same
   verify path serves login step-up (R2-003 calls it) and any sensitive-action step-up.

3. **Recovery codes.** `getMfaRecoveryCodes` regenerates a fresh single-use set (invalidating the old), shown
   once (`MfaRecoveryCodes`, `generatedAt`). A recovery code is accepted anywhere a TOTP code is, and is
   consumed on use.

4. **Disable.** `disableMfa` (`MfaDisableRequest`) re-authenticates with a current TOTP/recovery `code` or the
   account `password`, then clears the secret and recovery codes. Refuse to disable for a user whose role
   **requires** MFA unless an admin is performing a reset (admin reset lives in the user-management API,
   R2-005; expose the needed service method here and note the dependency).

5. **Enforcement.** `MfaStatus` (`enabled`, `enrolledAt`, `required`) reports whether a role the user holds
   (Admin/Operator) requires MFA. In the auth flow (R2-003) and `AccessPolicy` (R2-004), when MFA is required but not
   enrolled, allow only the enrollment endpoints and the profile, and gate every other write behind enrollment;
   when enrolled, require a verified TOTP step-up at login to issue a full session.

**Migration.** Add the next free additive Flyway migration `V{n}__mfa.sql` (`n` one past the highest `V*` now
present — read the directory; R2-001…R2-013 claim V14 upward): columns on `user` (`mfa_secret_encrypted`,
`mfa_enabled`, `mfa_enrolled_at`) and a `user_recovery_code` table (user id, code hash, used_at). Additive only.

## Contract

The four ops are authored `planned`; implement them to their schemas (secrets/codes read-only-once or
write-only as authored). Extend a schema / add an error code if needed, regenerate Postman
(`python3 scripts/generate-postman.py`), but **leave `x-foresignal-status: planned` and do not regenerate the
SDKs** (R2-027 flips + regenerates). If you add a TOTP/QR dependency, add it to the build and
`THIRD_PARTY_NOTICES.md`. `docs/OpenAPI.json` is the only contract.

## Tests to write (do not run)

- `TotpServiceTest` — a known secret + time yields the expected code; ±1 window; a used code is rejected (replay).
- `MfaEnrollmentIT` — enroll → verify activates MFA and returns recovery codes; wrong code does not activate.
- `RecoveryCodeIT` — a recovery code authenticates once then is consumed; regenerating invalidates the old set.
- `MfaDisableIT` — disable needs a code or password; a required-MFA role cannot self-disable.
- `MfaEnforcementIT` — an Admin/Operator without MFA is gated to enrollment; with MFA, login needs a step-up.
